# 远程服务器容器工作流

服务位于远程容器时使用本文件，在真实环境中完成“连接 → 快照 → 复现 → 单变量修复 → 回归 → 交付”。

## 首轮收集

首轮只询问用户无法从服务器可靠发现的信息，条目和措辞以「推荐首轮提问」为准：服务器/容器/认证/代理（PD 分离含全部节点，没有代理不阻塞排障）、每个容器内模型服务的启动脚本、异常与复现信息、验收标准。

不要询问容器运行时、服务端口、日志路径、脚本引用文件、停止/重启命令或 PD 角色；连接后自行发现。默认允许读取容器。

### 推荐首轮提问

```text
请提供：
1. 服务涉及的全部服务器 IP、用户、认证方式和各自容器名（PD 分离请包含所有节点；SSH 默认端口为 22，非默认端口请注明；已有可用 SSH 密钥/会话时无需密码，否则请提供密码；相同认证信息可只写一次）；容器内访问外网的代理，没有则无需提供；
2. 每个容器内模型服务的启动脚本绝对路径，或直接粘贴脚本；一个容器运行多个模型服务时请分别提供；
3. 详细的异常情况和复现信息（异常请求/评测、期望与实际现象、出现概率及触发条件等）；
4. 判定问题已经解决的验收条件（需要通过的 bad case/数据集，以及目标分数或相对基线差值）；暂时没有时请直接说明。

另外，您是否还有其他可能有助于复现或定位问题的有效信息可以补充？如有请提供，这对加速定位并修复问题非常重要。
```

优先使用用户确认可用的 SSH 密钥或现有会话；只有密钥/会话不可用、连接失败或用户选择密码认证时才请求密码。密码和代理凭据只用于认证或临时联网，不复述、不写入命令参数、长期文件、日志或报告。设置代理时保留并补充内网服务器、PD 节点和服务地址到 `NO_PROXY`，避免内部流量经过外部代理。

连接时先使用端口 `22`。只有用户主动提供非默认端口，或默认端口连接失败且现象指向端口配置时，才询问或尝试其他端口。

## 1. 验证目标并冻结快照

在所有节点确认 hostname、时间、容器 ID、镜像 digest、监听端口和 PID，并从模型服务启动脚本、实际 argv、rank 与网络参数还原 PD/TP/DP/EP 拓扑。避免无过滤地打印环境变量或 `docker inspect`。

修改前保存：

- `vllm`、`vllm-ascend`、PyTorch、`torch_npu`、CANN、driver/firmware、Python 和 commit；
- 模型/tokenizer revision、量化配置、关键权重文件哈希；
- 模型服务启动脚本及引用文件、实际 argv、工作目录和必要环境变量；
- NPU 型号/可见设备、节点/rank 映射、容器挂载、健康状态和相关日志。

装了 server-management skill 时，用本 skill 的 `scripts/env_snapshot.py --host <机器> [--container <容器>]` 一键采集：版本矩阵（vllm/vllm-ascend/torch/torch_npu）、npu-smi 卡状态（24.x/26.x 双格式解析）、driver、容器配置（镜像/挂载/ShmSize/IPC/特权）、昇腾运行时环境变量、运行中 vllm 进程的实际环境与自定义 CANN 库加载数，输出 JSON 存档。诊断前后各拍一次，diff 能发现环境被改动导致的复现失效。未装该 skill 时按下方手工流程采集。

优先运行 `collect_env.py` 一次性收集版本信息：vllm-ascend 源码 checkout 的仓库根目录自带；环境没有时按目标版本从 https://github.com/vllm-project/vllm-ascend/blob/main/collect_env.py 下载后运行，较新 vLLM 也可用 `vllm collect-env` 子命令。诊断快照必须脱敏，不包含密码、token 或受限业务数据。

## 2. 在原配置复现

先发送最小请求确认异常入口，再按真实条件增加输入长度、并发、长短混部、MTP/cache/async 等因素。每轮设置有限请求数、超时和停止条件。

关联记录请求 ID、时间戳、原始请求/响应、token IDs、服务端日志和 NPU 异常。流式请求同时保留每个 delta 与最终聚合文本。未复现时优先核对客户端模板、流量入口、请求参数、模型 revision、负载形态和节点差异，不随机堆环境变量。

## 3. 单变量容器迭代

默认直接在目标非生产测试容器修改源码、启动参数或依赖并重启服务。每轮维护一条实验记录：假设、唯一变更、文件/启动参数 diff、请求集、失败数/分数、性能和结论。

迭代顺序：

1. 记录相关文件路径和原始哈希，将文件备份到明确目录或宿主机；
2. 保存当前模型服务启动脚本、实际进程参数和实验编号；
3. 应用一个假设对应的变更，按实际管理方式重启并完成健康检查；
4. 先跑最小 bad case，再跑代表性集合；
5. 无效则恢复本轮备份，不叠加未经证实的修改；
6. 有效则先标记为候选修复，做 A/B/A 或交互矩阵并扩大回归；后续状态判定与推进按 [SKILL.md](../SKILL.md)「状态推进」执行。

不要直接 `kill -9`，除非正常停止失败且用户允许。生产容器按「暂停有副作用操作」执行。

## 4. 保存成果与回滚

将以下产物保存到宿主机、工作区或用户指定目录：

- 从原始状态到最终状态的完整 diff/patch、修改文件及备份哈希；
- 脱敏后的启动命令、复现脚本、回归结果和日志路径；
- 恢复原文件和启动配置的精确回滚步骤；
- 最终 Markdown 报告。

默认不要求构建镜像或提交源码仓；用户要求生产化交付时再生成正式 commit、镜像或部署清单。

## 暂停有副作用操作

用户声明为生产环境、明确限制权限、唯一复现会影响其他租户、没有可恢复备份，或需要未授权的数据/节点时，暂停相关写操作并说明。仍可继续只读检查、整理证据和设计最小复现。
