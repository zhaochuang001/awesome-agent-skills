# 远程服务器容器工作流

服务代码、运行环境或模型位于远程服务器容器时使用本文件。目标是在真实环境中安全地完成“连接 → 快照 → 复现 → 迭代 → 修复 → 回归”，而不是根据零散描述猜测。

## 首轮只收集四类信息

### 连接与认证

- 服务涉及的全部服务器 IP/hostname、SSH 端口、用户名、密码和容器名；
- 多机 PD 分离服务必须覆盖所有 Prefill/Decode 服务器及容器；用户不知道角色时不追问，连接后自行识别；
- 多台服务器凭据相同时允许用户只说明一次。

首轮必须明确请求 SSH 密码，不得因为本机可能存在 SSH key/会话而省略密码字段，也不要在首轮末尾用“优先使用现有 SSH key/会话”弱化这项要求。用户明确选择已配置密钥时再改用密钥。密码收到后只用于建立连接：不复述、不展示在进度更新中，不使用 `sshpass`，不写入命令参数、环境变量、脚本、shell history、诊断文件或报告；优先通过交互式 SSH 提示输入。内网 IP 遵循本机 `no_proxy`，不要经外部代理访问。

### 容器与服务

- 每个容器只需询问容器名；运行时、镜像、挂载、代码/模型路径和健康状态进入服务器后自行发现；
- 每个容器询问启动脚本的绝对路径，或让用户直接提供具体脚本内容；
- 默认允许进入容器读取启动脚本。脚本引用的 `.env`、配置文件和二级脚本由代理自行追踪；
- 服务端口、日志路径、实际进程命令、工作目录、进程管理器及停止/启动/重启方式从脚本、容器和运行进程中自行确定，不向用户逐项询问。

### 异常与复现

只用一句自然语言请求用户提供“详细的异常情况和复现信息”，可以在括号中提示包括：异常请求或评测命令、期望/实际输出、失败次数/总次数、触发并发与输入长度、stream/采样参数/seed、已知正常版本和最近变更。不要拆成十几个必填字段；用户给出部分信息后先进入环境验证，其余可从请求脚本、日志和运行配置补齐。

### 用户验收标准

询问用户用什么条件判断精度问题已经解决，只需让用户给出必须通过的 bad case/数据集，以及目标分数或相对正常基线的允许差值。不要询问目标负载下的测试次数、允许失败数或吞吐/时延容忍度；这些由代理根据复现条件设计回归并在结果中报告。

用户暂时没有明确标准时，不要求其凭空决定。先说明将在获得正常基线和故障发生率后提出量化验收方案，并在开始最终回归前让用户确认。用户未确认前，可以继续只读检查和复现，但不能自行宣布问题已经解决。

### 推荐首轮提问

保持简短，可按以下结构提问：

```text
请提供：
1. 服务涉及的全部服务器 IP、SSH 端口、用户、密码和各自容器名（PD 分离请包含所有节点；相同账号密码可只写一次）；
2. 每个容器的启动脚本绝对路径，或直接粘贴启动脚本；
3. 详细的异常情况和复现信息（异常请求/评测、期望与实际现象、出现概率及触发条件等）。
4. 判定精度问题已经解决的验收条件（需要通过的 bad case/数据集，以及目标分数或相对基线差值）；如果暂时没有，请直接说明，我会根据正常基线提出方案供您确认。

另外，您是否还有其他可能有助于复现或定位问题的有效信息可以补充？
```

不要再询问是否生产、是否允许读取容器、脚本引用文件、停止/重启命令、服务端口、日志路径或逐项操作授权。默认非生产并允许正常排障操作；用户主动声明生产环境或限制权限时再收紧操作。

## 进入环境后的顺序

### 1. 验证目标

先在所有服务器上确认 hostname、时间/时区、内核、运行时、容器 ID、镜像 digest、服务监听端口和 PID，避免连接到错误节点或相似容器。结合启动脚本、进程参数、rank/网络配置识别 Prefill/Decode 角色和完整 PD 拓扑，不依赖用户预先整理。

不要直接打印完整环境变量或未经筛选的容器 inspect 结果；它们可能包含 registry token、API key 和业务凭据。只查询精度排障所需的字段，并在报告中脱敏。

### 2. 创建只读快照

在修改前记录：

- `vllm`、`vllm-ascend`、PyTorch、`torch_npu`、CANN、driver/firmware、Python 和 commit；
- NPU 型号、可见设备、TP/DP/EP、节点/rank 映射；
- 实际运行进程的 argv、工作目录和选定环境变量；
- 启动脚本及其引用文件的内容与哈希，并记录它们和实际 argv 的差异；
- 模型/tokenizer revision、量化配置和关键权重文件哈希；
- 容器 mount、镜像 digest、健康状态和近期相关日志。

若容器中存在 `collect_env.py`，运行并保存输出。把快照存到用户允许的诊断目录；其中不得包含凭据或受限业务数据。

### 3. 在原配置复现

先对运行中的原服务发送最小请求，确认从哪个入口出现异常。然后按用户提供的真实条件逐步增加输入长度、并发、长短混部、MTP/cache/async 等触发因素。每轮设置有限请求数、超时和停止条件。

同步记录请求 ID、时间戳、原始请求、原始响应、token IDs、服务端日志和容器/NPU 异常。流式接口同时保留每个 delta 与最终聚合文本，排除客户端重复拼接。

未复现时优先核对流量入口、客户端模板、请求参数、模型 revision、负载形态和节点差异；不要通过随机改环境变量“碰运气”。

### 4. 直接在目标测试容器迭代

默认这些容器是专门用于精度排障的非生产测试容器，可以直接修改源码、启动参数和依赖并重启服务，不要求另建测试容器、Git 分支或候选镜像。

每轮修改前：

1. 记录相关文件绝对路径和原始哈希；
2. 将即将修改的文件备份到容器内明确的诊断备份目录，或复制到宿主机；
3. 保存当前启动脚本、实际进程参数和本轮实验编号；
4. 只应用一个假设对应的变更，确保可以精确回滚。

变更无效时恢复本轮备份，不叠加未经证实的修改。变更有效时生成 diff/patch，并将其与必要的修改文件、复现脚本和测试结果复制到容器外；容器内临时修改不得成为唯一成果。用户明确说明是生产容器时，再改用隔离测试环境和更严格的变更确认。

### 5. 单变量迭代

维护实验账本，每轮记录：假设、唯一变更、文件 diff/启动参数、镜像或代码版本、重启方式、请求集哈希、失败数/总数、任务分数、首差异 token/logits、性能和结论。

推荐循环：

1. 从原配置确认 bad case；
2. 应用一个可回滚变更；
3. 用原启动方式重启候选服务并等待健康检查；
4. 先跑最小 bad case，再跑代表性集合；
5. 无效则回滚，不叠加未经证实的改动；
6. 有效则做 A/B/A 或交互矩阵，判断是关联、规避还是根因修复；
7. 根据证据进入下一轮，直到满足验收标准或遇到需要用户决策的权限/代价边界。

服务进程应通过其实际管理器重启，不直接 `kill -9`，除非正常停止已经失败且用户授权。启动后检查健康端点、端口、容器状态、NPU 占用和日志，再发送精度请求。

### 6. 保存成果与回滚

最终交付应包括：

- 从原始状态到最终状态的完整 diff/patch；
- 修改前备份及其哈希、最终修改文件和保存位置；
- 完整但已脱敏的启动命令；
- 原 bad case、业务精度集、目标负载和性能结果；
- 恢复原始文件和启动配置的精确回滚步骤；
- 最终 Markdown 报告及其他产物路径。

默认不要求构建镜像或提交源码仓。只有用户要求把修复用于生产部署时，才进一步生成正式 commit、镜像或部署清单；否则以可复用的 diff/patch、修改文件、测试结果和报告作为交付物。

## 失败与暂停条件

默认非生产并允许正常排障操作。遇到以下情况暂停有副作用的操作并向用户说明：

- 用户明确说明目标为生产环境，而操作可能影响现有流量或其他租户；
- 用户明确限制修改、重启、安装依赖或压力测试；
- 唯一复现方法可能影响现有流量或其他租户；
- 回滚路径不明确，或当前容器/脚本没有可恢复副本；
- 需要访问未授权的模型、数据、凭据或其他节点。

仍可继续执行只读检查、整理现有证据和设计最小安全复现。
