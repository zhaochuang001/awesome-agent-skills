# 远程服务器容器工作流

服务代码、运行环境或模型位于远程服务器容器时使用本文件。目标是在真实环境中安全地完成“连接 → 快照 → 复现 → 迭代 → 修复 → 回归”，而不是根据零散描述猜测。

## 一次性收集的信息

### 连接与认证

- 服务器 hostname/IP、SSH 端口和用户名；
- SSH key、agent、已有认证会话或其他认证方式；
- 跳板机、VPN、网络分区和代理/`no_proxy` 要求；
- 是否需要 `sudo`，以及容器运行时权限；
- 多机部署时所有节点、主节点和 rank 映射。

优先让用户配置 SSH key/agent 或使用已有认证会话。若环境只能使用密码，密码应通过 SSH 的交互式提示或环境提供的安全凭据机制输入；不要让用户把密码发到对话，不使用 `sshpass`，不把密码放在命令参数、环境变量、脚本、shell history 或报告中。

### 容器与服务

- Docker、Podman、containerd/Kubernetes 等运行时和目标容器名/Pod；
- 镜像名称、tag 和 digest，容器创建时间及重启策略；
- 宿主机与容器内的代码、模型、配置、缓存和日志路径；
- bind mount/volume 映射，确认哪些修改会持久化；
- 服务启动脚本或编排配置的路径与完整内容，以及脚本引用的环境文件、配置文件和二级脚本；
- 当前运行 PID 的完整 argv、工作目录、关键环境变量、服务端口和健康检查；
- 进程由 shell、systemd、supervisor、docker compose、Kubernetes 还是其他系统管理；
- 正常的停止、启动和回滚方法。

### 首次响应规则

若用户尚未提供服务启动脚本，第一轮信息收集必须直接询问，不能只笼统地要求“提供环境信息”。至少询问：

1. 启动脚本或 compose/Kubernetes/systemd/supervisor 配置的绝对路径；
2. 文件完整内容，或进入容器后读取该文件的权限；
3. 脚本引用的 `.env`、配置文件和其他脚本路径；
4. 当前服务是否确实由该脚本启动，以及正常的停止、启动和重启命令。

脚本可能已经被修改、被包装器覆盖，或只用于生成最终命令。连接容器后必须将脚本展开结果与实际 PID argv、工作目录和关键环境变量对照。若用户无法提供脚本且没有读取权限，将其列为复现阻塞项，不根据猜测重建启动命令。

### 异常与复现

- 可直接执行的原始请求、数据集或调用脚本；
- 期望输出、实际原始响应、输出 token IDs、`finish_reason`/`stop_reason`；
- 必需的模型、语言、输入/输出长度、stream、采样参数和 seed；
- 并发、batch churn、KV-cache 压力、DP/EP/TP、跨机等触发条件；
- 失败次数/总次数、是否偶现、首次异常时间、已知正常版本；
- 客户端、网关、服务端日志的时间关联方式。

### 操作授权

明确用户允许哪些操作：只读检查、复制文件、修改启动参数、修改源码、容器内临时 patch、构建镜像、安装包、重启/停止服务、切换流量、执行低负载复现或压力测试。生产环境的服务重启、依赖安装、镜像替换和压力测试需要单独明确授权；问题排查授权不自动包含这些操作。

## 进入环境后的顺序

### 1. 验证目标

先确认 hostname、时间/时区、内核、运行时、容器 ID、镜像 digest、服务监听端口和 PID，避免连接到错误节点或相似容器。多节点服务对每个节点分别确认。

不要直接打印完整环境变量或未经筛选的容器 inspect 结果；它们可能包含 registry token、API key 和业务凭据。只查询精度排障所需的字段，并在报告中脱敏。

### 2. 创建只读快照

在修改前记录：

- `vllm`、`vllm-ascend`、PyTorch、`torch_npu`、CANN、driver/firmware、Python 和 commit；
- NPU 型号、可见设备、TP/DP/EP、节点/rank 映射；
- 实际运行进程的 argv、工作目录和选定环境变量；
- 启动脚本及其引用文件的内容与哈希，并记录它们和实际 argv 的差异；
- 模型/tokenizer revision、量化配置和关键权重文件哈希；
- 容器 mount、镜像 digest、健康状态和近期相关日志。

若容器中存在 `collect_env.py`，运行并保存输出。把快照存到用户允许的诊断目录；其中不得包含凭据或受限业务数据。

### 3. 在原配置复现

先对运行中的原服务发送最小请求，确认从哪个入口出现异常。然后按用户提供的真实条件逐步增加输入长度、并发、长短混部、MTP/cache/async 等触发因素。每轮设置有限请求数、超时和停止条件；生产服务未获授权时，不执行压力复现。

同步记录请求 ID、时间戳、原始请求、原始响应、token IDs、服务端日志和容器/NPU 异常。流式接口同时保留每个 delta 与最终聚合文本，排除客户端重复拼接。

未复现时优先核对流量入口、客户端模板、请求参数、模型 revision、负载形态和节点差异；不要通过随机改环境变量“碰运气”。

### 4. 建立安全迭代环境

优先级如下：

1. 使用同镜像、同模型和同拓扑的测试容器；
2. 使用当前容器的持久化源码挂载，并在独立分支或副本中修改；
3. 构建带明确 tag/digest 的候选镜像；
4. 只有在用户明确要求紧急临时验证时，才直接修改运行中容器，并先备份精确文件和记录哈希。

容器内临时修改在重建后会丢失。验证有效后必须同步到源码仓、Dockerfile、镜像或部署清单。不要把完整容器文件系统当作补丁交付。

### 5. 单变量迭代

维护实验账本，每轮记录：假设、唯一变更、文件 diff/启动参数、镜像或代码版本、重启方式、请求集哈希、失败数/总数、任务分数、首差异 token/logits、性能和结论。

推荐循环：

1. 从原配置确认 bad case；
2. 应用一个可回滚变更；
3. 用原启动方式重启候选服务并等待健康检查；
4. 先跑最小 bad case，再跑代表性集合；
5. 无效则回滚，不叠加未经证实的改动；
6. 有效则做 A/B/A 或交互矩阵，判断是关联、规避还是根因修复；
7. 根据证据进入下一轮，直到满足验收标准或遇到需要用户决策的权限/代价边界。

服务进程应通过其实际管理器重启，不直接 `kill -9`，除非正常停止已经失败且用户授权。启动后检查健康端点、端口、容器状态、NPU 占用和日志，再发送精度请求。

### 6. 持久化、灰度与回滚

最终交付应包括：

- 持久化源码或部署配置的 diff；
- 候选镜像 tag 和不可变 digest；
- 完整但已脱敏的启动命令；
- 原 bad case、业务精度集、目标负载和性能结果；
- 灰度范围、观测指标和停止条件；
- 恢复旧镜像/配置/代码的精确回滚步骤。

如果只有测试容器验证通过而未在目标拓扑验证，明确标为“候选修复”。如果只在运行容器中临时修改，明确标为“临时验证”，不得报告为已交付的持久修复。

## 失败与暂停条件

遇到以下情况暂停有副作用的操作并向用户说明：

- 无法确认目标服务器、容器或服务是否为生产；
- 缺少修改、重启、安装依赖或压力测试的授权；
- 唯一复现方法可能影响现有流量或其他租户；
- 回滚路径不明确，或当前容器/脚本没有可恢复副本；
- 需要访问未授权的模型、数据、凭据或其他节点。

仍可继续执行只读检查、整理现有证据和设计最小安全复现。
