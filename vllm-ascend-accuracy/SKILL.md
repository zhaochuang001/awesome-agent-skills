# vLLM Ascend 精度诊断与修复

目标不是停在问题定位，而是恢复到明确的正确性标准：用可复现证据找到最小致因，在用户授权范围内实施最小修复，并完成精度、稳定性和性能回归。不要仅凭输出表象归因，也不要一开始就用 `repetition_penalty`、提示词改写等方式掩盖系统性错误。

## 开始前

默认完成“复现 + 定位 + 实施修复 + 回归验证”。若服务位于远程服务器容器中，先读取 [references/remote-container-workflow.md](references/remote-container-workflow.md)，用一轮简短提问收集全部节点的连接/容器信息、启动脚本、异常复现信息和用户验收标准，再进入环境完成闭环；不要用长表格要求用户填写本可在服务器上自行发现的信息。

远程场景至少需要：服务涉及的全部服务器 IP/SSH 端口/用户/密码和各自容器名、每个容器的服务启动脚本绝对路径或脚本内容、详细的异常现象与复现信息，以及用户对“精度问题已解决”的验收条件。服务可能采用多机 PD 分离部署，不能默认只有一台服务器；若用户只给出一个节点，要确认是否还有其他 Prefill/Decode 节点。无需询问容器运行时、服务端口、日志路径、环境文件、二级脚本、停止/重启命令或 PD 角色，连接后从容器、启动脚本和实际进程中自行发现。

**服务启动脚本是必问项。** 如果用户首次描述中没有提供，只询问启动脚本的绝对路径或具体脚本内容；默认允许进入容器读取完整内容并继续追踪其引用文件。连接后将脚本与实际运行进程的 argv、工作目录和关键环境变量对照，不要假定脚本内容等于当前真实启动参数。

**SSH 密码是必问项。** 首轮提问必须明确出现“密码”，不能用“优先使用现有 SSH key/会话”等表述替代或省略；用户明确选择使用已配置密钥后，才可以不提供密码。密码仅用于认证，不得回显、写入命令参数、脚本、环境变量、日志或报告，优先通过交互式 SSH 输入。

**验收条件也是必问项。** 只让用户给出需要通过的 bad case/数据集，以及目标分数或相对正常基线的允许差值。用户暂时没有明确标准时，先基于正常基线和复现结果提出可量化方案，请用户确认后再将其设为完成判据；未经用户确认，不得自行定义“已解决”。不要要求用户预先给出目标负载下的测试次数、允许失败数或性能容忍度。

默认目标服务器上的容器是专门用于精度排障的非生产测试容器，并默认用户允许正常排障所需的读取、复制、低负载/压力复现、修改启动参数或源码、临时 patch、安装依赖及重启服务；可以直接在目标容器内迭代，不要求另建测试容器、Git 分支或候选镜像。每轮修改前备份相关文件并记录哈希，最终把 diff/patch 和必要产物保存到容器外。用户声明为生产环境或明确限制操作时，以其限制为准，并在高影响操作前确认。

收集或从现有日志中提取：

- 原始请求与原始响应、stream/non-stream、token IDs、`finish_reason`/`stop_reason`；
- 模型与 tokenizer 的来源、revision/哈希、chat template、量化方式和权重完整性；
- `vllm`、`vllm-ascend`、CANN、driver/firmware、PyTorch、`torch_npu`、Python、容器镜像及 commit；优先运行仓库的 `collect_env.py`；
- 完整启动命令、环境变量、并行拓扑、NPU 型号/节点数、并发与输入长度分布；
- bad case 的发生率、首次出现时间、最近变更，以及一个正常基线的同类信息。

访问在线资料时以与目标版本对应的官方文档、release note、GitHub issue/PR 和源码为准。`latest` 文档不能自动代表旧版本行为。

## 解决闭环

1. **建立访问与拓扑**：验证能进入所有服务器和容器，从启动脚本、实际进程和网络参数还原 PD 分离节点关系。默认非生产且允许正常排障操作；若用户声明为生产或有限权限，再明确相应边界。
2. **冻结环境快照**：在任何修改前记录镜像 digest、容器挂载、实际进程命令、启动脚本哈希、包/驱动版本、环境变量白名单、NPU 拓扑和当前健康状态。不要无过滤地导出可能包含密钥的环境或 `docker inspect`。
3. **锁定验收并复现问题**：把用户验收条件转成可执行测试；保存稳定 bad case 和代表性评测集，固定模型 revision、输入 token、chat template、采样参数、seed 与评测器版本。在原始容器和原始负载条件下复现，记录失败数/总数、原始响应、token 和关联日志；未复现前先补齐触发条件，不盲目改代码。
4. **建立正确基线**：优先使用已知正常版本、Transformers eager 或可用参考后端，以同一权重、tokenizer、输入 token 和解码参数对照。参考后端不同也要记录，不能把差异直接等同于 Ascend 缺陷。
5. **缩小致因**：验证输入/解析链路，并从 greedy、单并发、短上下文、eager、单卡/纯 TP、已知正常权重开始，逐项恢复量化、DP/EP、ACL Graph、MTP、cache、async、LoRA、structured output 等功能。
6. **选择修复层级**：优先修复最接近根因且影响最小的层级：请求模板/解析 → 版本和依赖 → 权重/量化 → 启动配置 → 调度/KV/通信/算子 → vLLM Ascend 源码。不要用上层参数掩盖下层计算错误。
7. **在目标测试容器迭代修复**：每轮只改一个假设对应的变量，修改前备份原文件，保存 diff、启动配置、测试结果和回滚点；无效则恢复备份，有效则继续回归。能采用已发布兼容版本或官方已合入补丁时优先使用。
8. **验证恢复**：先跑固定 bad case 和任务指标，再跑生产形态的长短请求、高并发、batch churn、KV 压力和目标并行拓扑。至少使用 A/B/A、版本回切或等价方法排除偶然性。
9. **评估代价并保存成果**：测量吞吐、TTFT、TPOT、显存及启动时间。将最终 diff/patch、修改文件、启动配置和回归结果复制到宿主机、工作区或用户指定目录，不要只留在可丢失的容器层；仅在用户要求生产化交付时再写回源码仓、构建镜像或修改部署配置。
10. **交付与防回归**：提供变更 diff、完整命令、验证结果、已知限制和回滚方法。将 bad case、评测配置和触发组合固化为自动化回归用例，并生成最终 Markdown 报告。

具体消融顺序、症状路由和已知问题模式见 [references/diagnostic-playbook.md](references/diagnostic-playbook.md)。确认致因或需要先恢复业务时，读取 [references/remediation-playbook.md](references/remediation-playbook.md) 并实施对应修复。要提交 issue 或交接给研发时，再读 [references/issue-report.md](references/issue-report.md)。

## 评测要求

- 将“输出异常率”和“任务得分下降”分开测量；乱码/复读检测只是筛查，不等于业务精度。
- 对齐数据集版本、split、few-shot、prompt/chat template、最大长度、采样参数和答案抽取器。
- 同时报告绝对分数、基线差值、样本数、失败率/方差和逐样本结果；随机采样至少使用多个 seed。
- 可用 `scripts/analyze_generations.py` 初筛 JSONL 中的空输出、Unicode 替换符、控制字符和 n-gram 复读。它不能替代任务指标或人工判定。

## 完成条件

只有满足用户已确认的验收标准，并同时满足以下条件，才将任务报告为“已解决”：

- 原 bad case 在修复配置上通过，并经回切能再次触发或有等价的因果证据；
- 代表性任务指标达到预先定义的阈值，而不只是输出看起来正常；
- 目标并发、上下文长度和并行拓扑下未出现同类异常，概率问题报告测试次数和上限估计；
- 已提供可执行变更、回归用例和回滚方法。
- 已生成最终 Markdown 报告，并向用户提供文件路径。

如果只能关闭功能、回退版本或启用确定性计算，应明确称为“已规避”，不要称为根因已修复。如果受限于硬件、权重或线上权限而无法实施验证，交付修复补丁/命令和未完成项，不要宣称问题已经解决。

## 最终 Markdown 报告

任务达到终态时，无论结果是已解决、已规避还是受阻，都要读取 [references/final-report-template.md](references/final-report-template.md)，在用户指定目录生成一份独立 `.md` 报告；用户未指定时，默认写入当前工作目录，文件名使用 `vllm-ascend-accuracy-report-YYYYMMDD-HHMM.md`，不得覆盖已有报告。

报告必须基于实际证据，区分已证实事实和假设，写明用户验收标准及逐项结果，并包含环境/PD 拓扑、复现、实验记录、根因、修改、精度与性能回归、遗留风险和回滚方案。不得包含 SSH 密码、token、私钥、内部凭据或未脱敏业务数据；冗长日志只引用路径和关键片段。最终回复中给出报告的可点击绝对路径。

## 输出格式

向用户交付：

1. 现象与影响范围；
2. 已证实事实、尚未证实的假设；
3. 对照/消融结果表；
4. 最可能层级与证据；
5. 已实施的修复、临时规避与性能代价；
6. 回归结果、复现/部署命令和回滚方案；
7. 剩余风险或待补信息。

不要虚构版本兼容性、环境变量效果或已知修复。涉及升级、降级、替换权重或改动线上服务时，先说明影响与回滚方式，再按用户授权执行。
