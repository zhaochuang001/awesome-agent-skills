# vLLM Ascend 精度诊断与修复

目标不是停在问题定位，而是恢复到明确的正确性标准：用可复现证据找到最小致因，在用户授权范围内实施最小修复，并完成精度、稳定性和性能回归。不要仅凭输出表象归因，也不要一开始就用 `repetition_penalty`、提示词改写等方式掩盖系统性错误。

## 开始前

先确认用户要的是快速恢复、根因修复、精度评测，还是缺陷报告；如果没有说明，默认完成“复现 + 定位 + 实施修复 + 回归验证”。若服务位于远程服务器容器中，先读取 [references/remote-container-workflow.md](references/remote-container-workflow.md)，一次性收集连接、容器、启动方式、复现条件和操作授权，再进入环境完成闭环；不要在缺少实际环境时只给通用建议便结束。

远程场景至少需要：服务器地址与 SSH 用户/端口/认证方式、跳板或 VPN 要求、容器运行时和容器名、容器内代码/模型/启动脚本路径、服务端口与日志位置、异常请求和期望/实际输出、触发并发/长度/概率，以及允许执行的操作。优先使用 SSH key、agent 或已有认证会话；不要要求用户把明文密码粘贴到对话中，也不要把凭据写进命令、文件、日志或报告。

收集或从现有日志中提取：

- 原始请求与原始响应、stream/non-stream、token IDs、`finish_reason`/`stop_reason`；
- 模型与 tokenizer 的来源、revision/哈希、chat template、量化方式和权重完整性；
- `vllm`、`vllm-ascend`、CANN、driver/firmware、PyTorch、`torch_npu`、Python、容器镜像及 commit；优先运行仓库的 `collect_env.py`；
- 完整启动命令、环境变量、并行拓扑、NPU 型号/节点数、并发与输入长度分布；
- bad case 的发生率、首次出现时间、最近变更，以及一个正常基线的同类信息。

访问在线资料时以与目标版本对应的官方文档、release note、GitHub issue/PR 和源码为准。`latest` 文档不能自动代表旧版本行为。

## 解决闭环

1. **建立访问与边界**：验证能进入正确服务器和容器，确认是否为生产服务，以及读日志、复制文件、修改代码、重启服务、安装依赖和执行压力测试的授权范围。未授权的变更和负载测试不得执行。
2. **冻结环境快照**：在任何修改前记录镜像 digest、容器挂载、实际进程命令、启动脚本哈希、包/驱动版本、环境变量白名单、NPU 拓扑和当前健康状态。不要无过滤地导出可能包含密钥的环境或 `docker inspect`。
3. **定义并复现问题**：保存稳定 bad case 和代表性评测集；固定模型 revision、输入 token、chat template、采样参数、seed 与评测器版本。在原始容器和原始负载条件下复现，记录失败数/总数、原始响应、token 和关联日志；未复现前先补齐触发条件，不盲目改代码。
4. **建立正确基线**：优先使用已知正常版本、Transformers eager 或可用参考后端，以同一权重、tokenizer、输入 token 和解码参数对照。参考后端不同也要记录，不能把差异直接等同于 Ascend 缺陷。
5. **缩小致因**：验证输入/解析链路，并从 greedy、单并发、短上下文、eager、单卡/纯 TP、已知正常权重开始，逐项恢复量化、DP/EP、ACL Graph、MTP、cache、async、LoRA、structured output 等功能。
6. **选择修复层级**：优先修复最接近根因且影响最小的层级：请求模板/解析 → 版本和依赖 → 权重/量化 → 启动配置 → 调度/KV/通信/算子 → vLLM Ascend 源码。不要用上层参数掩盖下层计算错误。
7. **迭代实施修复**：每轮只改一个假设对应的变量，保存 diff、启动配置、测试结果和回滚点；能采用已发布兼容版本或官方已合入补丁时优先使用。源码修复必须添加修复前失败、修复后通过的回归测试。
8. **验证恢复**：先跑固定 bad case 和任务指标，再跑生产形态的长短请求、高并发、batch churn、KV 压力和目标并行拓扑。至少使用 A/B/A、版本回切或等价方法排除偶然性。
9. **评估代价并持久化**：测量吞吐、TTFT、TPOT、显存及启动时间。将最终修复写回持久化源码、镜像构建或部署配置，不要只留在可丢失的容器层。
10. **交付与防回归**：提供变更 diff、完整命令、验证结果、已知限制和回滚方法。将 bad case、评测配置和触发组合固化为自动化回归用例。

具体消融顺序、症状路由和已知问题模式见 [references/diagnostic-playbook.md](references/diagnostic-playbook.md)。确认致因或需要先恢复业务时，读取 [references/remediation-playbook.md](references/remediation-playbook.md) 并实施对应修复。要提交 issue 或交接给研发时，再读 [references/issue-report.md](references/issue-report.md)。

## 评测要求

- 将“输出异常率”和“任务得分下降”分开测量；乱码/复读检测只是筛查，不等于业务精度。
- 对齐数据集版本、split、few-shot、prompt/chat template、最大长度、采样参数和答案抽取器。
- 同时报告绝对分数、基线差值、样本数、失败率/方差和逐样本结果；随机采样至少使用多个 seed。
- 可用 `scripts/analyze_generations.py` 初筛 JSONL 中的空输出、Unicode 替换符、控制字符和 n-gram 复读。它不能替代任务指标或人工判定。

## 完成条件

只有同时满足以下条件，才将任务报告为“已解决”：

- 原 bad case 在修复配置上通过，并经回切能再次触发或有等价的因果证据；
- 代表性任务指标达到预先定义的阈值，而不只是输出看起来正常；
- 目标并发、上下文长度和并行拓扑下未出现同类异常，概率问题报告测试次数和上限估计；
- 性能代价在预算内，或用户明确接受该代价；
- 已提供可执行变更、回归用例和回滚方法。

如果只能关闭功能、回退版本或启用确定性计算，应明确称为“已规避”，不要称为根因已修复。如果受限于硬件、权重或线上权限而无法实施验证，交付修复补丁/命令和未完成项，不要宣称问题已经解决。

## 输出格式

向用户交付：

1. 现象与影响范围；
2. 已证实事实、尚未证实的假设；
3. 对照/消融结果表；
4. 最可能层级与证据；
5. 已实施的修复、临时规避与性能代价；
6. 回归结果、复现/部署命令和回滚方案；
7. 剩余风险或待补信息。

不要虚构版本兼容性、环境变量效果或已知修复。涉及升级、降级、替换权重或改动线上服务时，先说明影响与回滚方式，再按用户授权执行。
